# Subject Master (Subjects page): slice 0 (read-only audit and plan)

Status: written 2026-11-12. No code, schema or migration was touched. Branch `ui-redesign-pilot`, nothing pushed. Counts only on `sms_db` (no subject code or title was read or printed); structure read from `sms_db_uitest`. A synthetic 5,000-row timing was run in a throwaway schema (dropped).

## 1. What the Subjects page does today

- **Files:** `modules/curriculum/pages/subjects.php` (261 lines), `assets/subjects-redesign.js` (635 lines, the only script loaded), `assets/subjects.js` (642 lines, not loaded anywhere), `http/subject_actions.php`, `SubjectService`, `SubjectRepository`. No page-specific CSS file; it relies on `curriculum.css` and `csms-typography.css`.
- **Screens:** (a) *Landing:* program/strand cards in College and SHS sections with a client-side search and category tabs. (b) *Program view* (`?program_id=`): back link, breadcrumb, plain Curriculum and Version selects, year tabs, a search/year/semester/status filter row, and a **grouped list by year and semester** (cards, not a table) for the chosen version's placements. Three dialogs: details (with where-used from `assignment_actions.php?action=mapping_list`), create/edit, archive confirm.
- **Actions and permissions:** page needs `subject.view`; a program view also needs `program.view` + `curriculum.view`. `list`, `contexts`, `get` need `subject.view` (filters by program, curriculum, version, year, semester also need `curriculum.view`; `CurriculumReadScope::enforceInput` hides draft versions from restricted roles). `create` (`subject.create`), `update` and `archive` (`subject.update`), all POST + CSRF, audited. **New Subject exists only inside a program view and only for a role that also has `program.view`, `curriculum.view` and `curriculum.update`** (it creates the subject and places it in the selected version). Export link needs `curriculum_export.view`.
- **Old classes still present:** `curriculum-modal` (three dialogs), custom tab and filter classes (`subject-category-tabs`, `subject-year-tabs`, `subject-list-controls`, `search-control`, `form-field` selects instead of `csms-select`), a custom grouped list instead of `csms-ctable`, `subtle-text`, `subject-empty-state`. A dead `if (false)` block still carries the old master list with `domain-card`, `domain-table`, rows selector and an undefined `$subjectColumnCount`.
- **There is no all-subjects list in the UI.** The old master list is dead code. A subject can only be reached through a version it is placed in, so **a subject that is placed nowhere cannot be found, edited or archived from the page** (1 such subject in `sms_db`). Search covers only the loaded version.
- **Scale behaviour:** the API is server-side (search, status, filters, rank-before-page, `per_page` 10/20/50 only; no sort parameter). The page ignores that: `loadVersionSubjects` loops every page of 50 for the chosen version and filters, groups and sums **in the browser**; the landing loads all programs at once (`contexts` returns every program unpaged). At 5,000 subjects in one list this would be 100 requests and one 5,000-row render, and the "master list" does not exist anyway. Database side (synthetic 5,000 subjects, best of 3): count 1 ms, title search over code and title 17 ms, first page 3 ms, deepest page 12 ms, search page 19 ms. **No index or migration is needed for listing**; only the UI and the endpoint contract (sort, `per_page` 100, usage count) need work.

## 2. Data model (`subjects`)

- Columns: `id`, `subject_code` varchar(60), `subject_title` varchar(255), `description` text, `units` decimal(6,2) NOT NULL default 0, `lecture_units` and `laboratory_units` decimal(6,2) NULL, `status` varchar(20) `active|inactive` (CHECK), `created_by`, `created_at`, `updated_at`, `archived_at`, `archived_by`, `archive_previous_status`.
- Constraints and indexes: unique `uq_subjects_code`; indexes on status, created_by, (`archived_at`,`archived_by`); CHECKs `units >= 0`, lecture and lab `>= 0 or NULL`. Collation `utf8mb4_unicode_ci`: **code uniqueness is case-, accent- and trailing-space-insensitive** (the validator trims; no uppercase normalisation and no format rule). Title search has no index (not needed, see above).
- **Units:** one number, `units`, plus optional lecture and laboratory units; nothing says whether these are credit units or hours, and there is no rule that lecture + lab equals units. The validator accepts 0 to 9999.99. `sms_db` counts: 55 subjects (52 active, 3 inactive, 0 archived); units never null or 0; lecture and lab both set on 2 and their sum equals units on both; no description set; no untrimmed or non-uppercase code.
- **Classification:** **no category, type or classification column anywhere** (`subjects`, `curriculum_version_subjects`, `curriculum_versions`; no lookup table). Stored per placement: `year_level`, `semester`, `sequence_order`, `is_required` (56 of 56 placements required). Elective membership exists only as elective groups (1 group, 4 members). Prerequisites: 7 rows. So 0 of the 54 placed subjects carry a category (there is no field to set).
- **Delete vs deactivate:** there is **no delete** (no endpoint; every foreign key to `subjects` is RESTRICT). A subject is edited to `inactive`, or archived (Archive Center `archive('subject')`: active only, sets `inactive` + `archived_at`, previous status kept, restore re-validates).
- **Audit:** `SUBJECT_CREATE` and `SUBJECT_UPDATE` store only `subject_code` and `status` (no old and new values, so a units or title change cannot be reconstructed from the audit log); `SUBJECT_ARCHIVE` and `SUBJECT_RESTORE` store identifier and statuses.
- **Read scope:** subject rows themselves are readable with `subject.view`; version filters and placement context are refused or hidden for roles without `curriculum.view_unapproved` (`enforceInput`, `_include_placement_context` false when restricted).

## 3. Usage protection: every consumer

`sms_db` counts: 56 placements, 54 distinct subjects placed (1 unplaced), max 2 versions per subject (average 1.04), 7 prerequisite rows, 2 equivalencies, 2 program assignments, 4 elective members, 2 grade weighting schemes, 0 subject-specific compliance rules, 0 subject snapshots. All 6 versions are `not_started` (3 active, 3 draft), so **0 subjects are in a protected version today**. `reported_offerings` does not exist in `sms_db` (migration 029 is not applied there).

| Consumer | Link | What happens today |
|---|---|---|
| Placements (`curriculum_version_subjects`) | FK RESTRICT | `SubjectService::update` calls `assertMasterEditable('subject', id, data)`: if **any field changed** (title and description included) and the subject is placed in **any** version that is not editable (approved, under review, archived, reference, or proposed in a non-draft state), the update is refused. Placed only in editable versions: it succeeds and those drafts change immediately. Unchanged data is a no-op. Archive uses the same guard. |
| Prerequisites (`curriculum_subject_requirements`) | by version placement | Protected through the placement guard above; no separate rule. |
| Grade weighting | through placement | Protected through the placement guard. |
| Elective groups (`curriculum_elective_group_subjects`) | `subject_id`, no FK to `subjects` | **Not checked**: a member that is no longer placed (a known legacy defect shape) or in a version the guard does not see is editable freely. |
| Equivalencies (`subject_equivalencies`) | FK RESTRICT both sides | **Not checked.** A subject used only in equivalencies can have its code, title or units changed with no warning; stored decisions keep the subject id, not the old numbers. |
| Program assignments (`program_subject_assignments`) | FK RESTRICT | Not checked. |
| Offering history (`reported_offerings`, migration 029) | FK RESTRICT; reports match on `subject_code` at report time | **Not checked.** Changing a code makes later external reports for the old code fail as "unknown subject"; past rows keep the subject id. |
| Compliance rules (`compliance_rules.subject_id`) | FK RESTRICT | Not checked; changing units changes future results (stored runs are snapshots). |
| Version snapshots (`curriculum_version_subject_snapshots`) | captured on revision clone and reference attach | Comparison and history read these, which is what protects the history of a revision; approved versions otherwise read **live** subject units. |

**Places where a unit change could silently alter an approved or archived version:** none through the page today (the placement guard covers every field and every non-editable version). The weak points are (1) the guard is all-or-nothing per field set, so a title typo cannot be fixed on a subject in an approved version, which will push users to workarounds; (2) the guard does not cover consumers that are not placements (equivalencies, electives, offering history, compliance rules, program assignments), so an edit there changes meaning without any warning or audit detail; (3) approved versions compute totals and exports live from `subjects.units`, so any future code path that bypasses `SubjectService::update` (an import, a direct SQL fix) would change an approved total silently. S2 addresses (1) and (2).

## 4. Classification gap (for Compliance)

- **Not stored anywhere** (section 2). Without it Compliance can evaluate only the total-units rule; general education, PE, NSTP and the CMO 25 component table cannot be counted (Compliance_Plan.md section 15).
- **Categories, from the sources only** (as a data-driven lookup, each with its source): *General education core* and *General education elective* (CMO 20 s.2013), *Mandated Rizal course* (CMO 20, "mandated by law"), *Common courses*, *Professional courses*, *Professional electives*, *Additional mathematics* (CMO 25 s.2015 Sec. 8.1 table; its "General Education" row is the sum of the three CMO 20 groups), *Physical education (PATHFIT)* (CMO 39 s.2021), *NSTP* (RA 9163), and *Other / not classified* (the absence of a value). "Mandatory Elective" and "Free Elective" are **not** used (not confirmed by BCP).
- **Where it should live (decision, section 6 S3):** a classification is a statement about a subject *in a program*, because the CMOs classify per program (the same subject can be a general education course for one program and a professional course for another). Putting it on the subject alone is wrong for shared subjects; putting it on the placement ties it to the version lifecycle (an approved version could not be classified without a new revision). Recommendation: a **new table keyed by subject and program** (see S3), outside the version lifecycle, never an ALTER of `subjects` or `curriculum_version_subjects` (both are baseline-covered).
- **From the client's signed reply (kept as stated):** NSTP components are ROTC and CWTS; NSTP 1 is a prerequisite of NSTP 2. This plan does **not** decide whether NSTP units count inside a program's total; classification only records categories, and the Compliance rule decides how units are summed. Identifying "NSTP 1" and "NSTP 2" needs either an NSTP position on the classification or a rule wording such as "an NSTP-classified subject is a prerequisite of another NSTP-classified subject" using the existing prerequisite edges; open question below.

## 5. Naming and validation rules supported by sources

- Nothing BCP-specific is hardcoded and nothing is invented. No source gives a subject code format, so **no pattern is enforced**. Existing rules stay: required code and title, trimmed, unique case-insensitively, units 0 to 9999.99.
- The client said curricula are named program code + start year (for example "BSIT 2026"). That belongs to the Curricula module (`curriculum_code`, `curriculum_name`), not to subjects; it should be a hint or an advisory there, not a subject rule, and is out of scope here.
- Advisory only (not blocking, no outside default): a "similar code" notice on create when an existing code matches ignoring spaces, hyphens and case; an informational note when lecture + lab units differ from units. Units meaning (credit vs hours) stays a question for the client.

### S3: classification (migration 033; DEPENDS ON A DECISION)
- **Scope:** a data-driven category list (`subject_categories`: key, label, source document and section, sort) seeded only with the categories in section 4; the classification field in the dialog; a **column and a filter** on the list; a **bulk-assign tool**: choose a program, filter or select subjects, pick a category, **preview** every change (subject, old category, new category, rows that will not change), apply in one transaction with one audit batch id, and **undo** the batch (restores the previous values, only for rows not changed since, reported when some were). New permission (suggest `subject.classify`; adding a permission is a seed change to confirm). Compliance then evaluates general education, PE and NSTP units and the component table from the stored categories, with the "elective units count only up to the required amount" caution, and the NSTP 1 → 2 rule from prerequisite edges (decision below).
- **Files:** migration `033_subject_classification.sql` (new tables only, idempotent, rollback file), `SubjectClassification*` repository, service and actions, S1 page additions, `ComplianceValidationService` (new computation keys), tests. Nothing applied to `sms_db` by the build; the user applies after a backup.
- **Decision needed, options:**
  - **A. Subject level** (`subject_classifications(subject_id PK, category_key)`): simplest; one category per subject for all programs. Wrong when programs classify the same subject differently.
  - **B. Placement level** (`curriculum_version_subject_classifications(placement_id PK, category_key)`): exact per version; cloned with revisions; but approved or archived versions cannot be classified without a new revision, so the 6 existing versions would need revisions first.
  - **C. Program level** (`subject_program_classifications(subject_id, academic_program_id, category_key)`, unique pair) — **recommended**: matches how the CMOs classify (per program), covers every version of the program, works for already-approved versions because it is metadata, and makes "assign this category to these subjects in BSIT" a natural bulk action. Cost: a subject re-categorised between curriculum versions of the same program needs a note; the compliance run records the categories it used.
- **Tests:** migration twice on a clone, bulk preview matches apply, undo, a changed-since row refused on undo, permissions, audit, Compliance results for GE, PE and NSTP once classified. **Manual checks:** classify the BSIT subjects through the tool, run validation, compare the per-category units with the CMO 25 table (54, 18, 48, 12, 0, 8, 6) without any verdict wording.
